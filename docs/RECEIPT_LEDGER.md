# 부분입금 원장 — 2.1.0 개발 계약과 구현 상태

## 현재 상태

현재 브랜치는 **2.1.0 개발 중**이다. 입금 원장의 계산·검증과 공식 `bill.receiptLedger` 필드, 저장 전 원문 대조, 서버의 기록 변경 보호를 구현했다. 동일 계산 소스에서 `server/Billing.gs`를 생성한다. 현재 화면과 `payment`, `historicalPayment`, `arrears`, `collectionStatus`는 아직 기존 납부 확인을 사용한다. 이 개발본은 원장 자료를 발견하면 편집·적용을 중단하고 원문 보관을 안내한다. 부분입금 입력 화면과 모든 수납 표시의 연결을 끝내야 이 임시 차단을 해제한다. 이 문서는 부분입금 기능 전체 완료나 운영 반영 기록이 아니다.

마지막 검증 릴리스 후보는 `candidate/independent-v206-18237dc`의 웹 2.0.6이다. 해당 ZIP·manifest·검증 결과를 그대로 보존한다. 현재 개발 소스를 그 후보와 같은 파일이라고 주장하지 않으며 2.1.0 후보 ZIP을 만들지 않는다. Google 운영 주소는 기존 1.0 배포 버전 4다.

## 실제 구현한 API

| API | 동작 |
|---|---|
| `openReceiptLedger(tenant, bill, billId, openedAt, options)` | 저장된 snapshot 고지서의 항목별 청구액·제외 상태·과거 확인 원문을 보관하고 빈 기록 목록 생성 |
| `validateReceiptLedger(ledger)` | 식별자·JSON·버전·시각·금액·취소 참조·기록 순서·모든 기록 시점의 항목 잔액 검사 |
| `appendReceiptEvent(ledger, event)` | 입력 원장을 바꾸지 않고 새 기록을 붙인 사본 반환. 동일 ID/동일 내용 재시도는 한 기록 유지, 다른 내용 재사용은 오류 |
| `receiptLedgerState(ledger, asOf, knownAt)` | 실제 입금 기준일과 기록 확인 시각을 구분해 과거 확인액·새 입금액·잔액·부분입금·항목 완납 계산 |
| `validateReceiptBill(tenant, bill, billId)` | 공식 원장의 부모 고지서 ID·청구액·제외·과거 확인 원문·추정 목록을 고지서 snapshot과 대조 |
| `assertReceiptDataTransition(before, after)` | 기존 고지서 기준과 원장 header/기록 prefix 보존, 새 입금/취소의 추가만 허용 |

API는 DOM·네트워크·기기 저장소를 사용하지 않는다. 원장 생성·추가를 호출했다고 실제 자료가 저장된 것으로 간주하지 않는다. 검증 함수는 원장 데이터의 내부 형식을 검사하며 서명·외부 입금 증명·저장 이력의 위변조 방지를 제공하지 않는다. 기존 고지서 또는 원장 객체를 직접 수정하지 않는다.

## 금액과 원장 개시

- 고지서는 `월:임차인ID`로 식별한다. 해당 월과 임차인의 저장된 snapshot이 필요하며 월세·관리비·승강기·호실·납기·계약 snapshot 누락을 임의로 채우지 않는다.
- `snapshotEstimated`가 있는 과거 고지서는 기본적으로 개시를 거부한다. 호출자가 검토를 명시한 경우에도 추정 항목 이름을 `estimatedFields`에 그대로 남긴다. 실제 입력 화면의 검토 절차는 아직 연결하지 않았다.
- 청구액은 기존 `charges/payment` 계산을 사용한다. 원장은 부가세 포함 최종 청구액을 기록한다. 기존 공급가 입력의 상한에 부가세가 더해진 금액도 정수로 보존하며 기존 공급가 `won` 검증 범위 자체를 바꾸지 않는다.
- 월세·관리비·전기·수도·승강기·오물의 6개 항목을 구분한다. 새 입금은 사용자가 지정한 한 항목에 귀속된다. 다른 항목·월에 잔액을 자동 배분하거나 초과입금·예수금·환급을 만들어 내지 않는다.
- 날짜가 없는 기존 완납 도장은 날짜 미지정 근거로 보존한다. 개시 날짜를 실제 입금 날짜로 바꾸지 않으며 과거 확인을 여러 가상의 입금으로 나누지 않는다. 기존 날짜의 짧은 표기는 기존 고지서 연도 해석과 같은 기준을 사용하고 원문도 유지한다. 기존 `null`·제외·추가 메타데이터도 보존한다.
- 고지서 청구액·제외 상태·계약 snapshot과 과거 확인 원문은 개시 이후 고정한다. 현재 저장 경계는 이 기준의 변경을 거부한다. 사용 가능한 재정산/금액 수정 UI와 명시적 이관 정책은 남아 있다.

## 기록 형식

최상위 항목은 `format`, `billId`, `openedAt`, `charges`, `legacy`, `estimatedFields`, `events`다. `format`은 `rental-receipts-v1`이다. 원장 및 새 기록의 모르는 필드는 제거하지 않고 지원 형식 오류로 중단한다.

입금 기록은 다음 형식이다. 아래 값은 개발 검사 예시이며 실제 사용자 입금이 아니다.

```json
{
  "kind": "receipt",
  "id": "receipt-example-1",
  "billId": "2026-10:t1",
  "item": "pay_rent",
  "amount": 30000,
  "receivedOn": "2026-10-02",
  "recordedAt": "2026-10-10T00:00:00.000Z",
  "note": "확인한 입금 기록 예시"
}
```

새 입금에는 양의 원 단위 정수와 실제 `YYYY-MM-DD` 입금일이 필요하다. 입금일은 기록 시각의 한국 날짜보다 미래일 수 없다. 고지서의 다른 항목 잔액을 빌려 초과 입금을 허용하지 않는다. 기록 ID는 원장 안에서 고유하고 고지서 ID는 부모 원장과 같아야 한다.

취소는 `kind: "void"`, 새 `id`, 같은 `billId`, `recordedAt`, 앞선 입금의 `reference`, 필수 `reason`으로 기록한다. 과거 확인의 정정은 `reference: "legacy:pay_rent"`처럼 명시한다. 존재하지 않는 입금·취소 기록의 재취소·중복 취소는 거부한다. 취소는 **기록 정정**이며 실제 환급을 뜻하지 않는다. 과거 확인 정정도 원본 도장·날짜·항목 기록을 삭제하지 않는다.

모든 기록은 개시 시각 이후의 유효한 UTC ISO 기록 시각 순서로 붙인다. 같은 ID 재시도에는 최초의 시각과 내용 전체를 사용한다. 재시도 때 시각이나 금액을 새로 만들면 동일 요청으로 취급하지 않는다.

## 조회 의미

- `asOf`는 실제 입금일을 비교하는 `YYYY-MM-DD` 기준일이다. 기준일을 생략하거나 짧은 날짜로 추정하지 않는다.
- `knownAt`은 어떤 기록까지 알고 있었는지를 정하는 UTC ISO 시각이다. 생략하면 원장의 마지막 기록 시각을 사용한다. 개시 이전의 지식 상태는 이 원장으로 재구성하지 않는다.
- 기본 조회는 현재 알려진 취소를 반영해 과거 집계를 정정한다. 취소 전 상태를 확인하려면 취소 기록 이전 `knownAt`을 명시한다. 두 날짜 축을 실제 입금일과 취소 기록일의 혼합 값으로 대체하지 않는다.
- 결과의 `legacyConfirmed`는 기존 확인 표시에 근거한 금액, `newReceived`는 새 원장의 실제 입금 기록 합계다. 날짜 미지정 과거 확인을 날짜별 실제 현금 입금으로 보고하지 않는다.
- 항목과 전체에서 `청구액 = 확인액 + 잔액`을 유지한다. 제외 항목에는 입금을 추가하지 않는다. 월세 110,000원에 30,000원과 80,000원을 기록하면 월세 잔액은 80,000원 → 0원이지만 다른 항목이 남아 있으면 전체 완납으로 표시하지 않는다.

## 개발 2단계: 공식 저장 경계

`RentalCore.validateData`는 공식 원장을 검증하며 고지서를 자동 보정하지 않는다. 보관된 임차인이 없어도 해당 고지서 snapshot으로 검사한다. 기존 숫자 문자열과 nullable 과거 확인은 의미와 원문을 유지한다. `persist`와 `persistChecked`는 실제 기기 저장 원문을 다시 읽어 변경 전후를 비교한 뒤 하나의 상태 키를 쓴다. `persistChecked`의 창 간 저장 token 검사도 유지한다. 원장을 가진 고지서/월 삭제, 오래된 백업으로 기록 제거, header 변경, 기록 교체·재정렬은 저장 전에 중단한다. 최초 개시에서도 기존 가격/과거 확인/계약 snapshot을 동시에 바꿀 수 없다. 취소는 기존 기록을 그대로 두고 새 기록을 추가한다.

새 로컬 서버 소스는 원장이 있는 데이터의 GET/POST에 `receiptLedgerProtocol: "rental-receipts-v1"`을 요구한다(GET에서는 query parameter). 쓰기는 변경 전 또는 후에 원장이 있으면 요구하며, 구형 writer가 원장 필드 자체를 빼더라도 거부한다. capability `receiptLedgerStorage`는 **저장 형식 지원**만 뜻한다. 기존 `expectedRevision`, `requestId`, 잠금, 복구 원문, chunk 저장, 저장 후 재조회, 재시도 중복 검사와 별도로 기존 원장 header와 prefix를 대조한다. 다른 기기의 신규 revision은 충돌로 중단한다. 이 코드는 실제 Google 운영 서버에 배포하지 않았다.

현재 UI에는 임시 보호를 연결했다. 원장 자료로 시작하면 지원 안내와 원문 내보내기를 제공하고, 파일 가져오기·기존 백업 복원·배경 Google 읽기·수동 저장은 기존 기기 자료와 원문을 유지한다. 파일 확인은 공식 형식 검사와 UI 적용 가능 여부를 구분한다. 원문 파일은 `recoveryRaw`의 각 저장 키에 원래 문자열을 보관하며 `reason: "receipt-interface-pending"`으로 구분한다. 이 임시 단계에서 지원되지 않는 자료를 손상으로 표시하지 않는다.

현황 문서의 수납 계산 연결도 남아 있어 원장이 있는 자료의 Docs 생성은 `unsupported`로 중단한다. 원장 DB 저장 확인 결과와 문서 상태는 독립적으로 반환한다. Calendar 계약 일정은 수납과 별개이며 기존 동작을 유지한다. 독립 앱의 모든 저장 내용을 외부 서명 또는 실제 은행 입금 증명으로 보장하는 기능은 아니다.

## 개발 1단계 검사 기록

새 단위 검사 15개는 snapshot 개시·추정 검토, 과거 원문/날짜 미지정/nullable 값, 여러 입금·취소·과거 확인 정정·동일 ID 재시도, 부가세 포함 상한·날짜·한국 자정, 초과·다른 고지서·잘못된 필드와 JSON 키, JSON 왕복과 기존 납부 동작 유지, 생성한 GAS 소스의 로컬 VM 계산 일치를 검사한다. 120개 재현 가능한 조합에서 최대 18개 입금 단계와 취소를 검사하고, 별도 누적한 기대 금액과 항목별 확인액을 대조한다.

최종 `npm run test:all` 통과: 단위 검사 118개 중 118개(새 원장 검사 15개 포함), 브라우저 검사 묶음 7개 중 7개, 전체 audit 65개 중 65개. 빌드·문법·생성 파일 일치도 통과했다. 검증 소스 커밋은 `da275ab`이며 최종 수행 시각은 2026-10-09T20:43:03.915Z이다. 실제 로컬 Edge의 PC/모바일 두 context에서도 번들 API 호출, 30,000원+80,000원 집계와 취소, 기존 자료·저장소·기존 납부 계산 보존을 확인했다. 부분입금 화면을 사용한 검사가 아니다.

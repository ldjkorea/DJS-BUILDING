# 독립앱 2.0 데이터 무결성 감사

## 범위와 권위

시작 HEAD는 5978818, 시작 작업 트리는 깨끗했다. 기준 태그 backup/independent-v1-5978818와 개발 브랜치 work/independent-v2를 사용한다. source-readonly의 push URL은 DISABLED다. GitHub 실조회 결과 출처 저장소는 이름과 달리 공개 상태였으며 공개 범위 변경이나 push는 하지 않았다.

Google 시트는 공유 자료의 권위, localStorage는 이 기기의 확인된 저장 및 미반영 수정, 고지서 snapshot은 과거 금액·계약의 권위다. UI/APK는 원본 데이터베이스를 새 구조로 이관하지 않는다. JSON schemaVersion 1, rental-sync-v2, 독립 접두사 rentalIndependent20261009.를 유지한다.

## 전체 저장 경로

1. UI 입력 검증 → 현재 도메인 후보 → RentalCore.validateData.
2. Web Locks 및 저장 토큰 대조 → 하나의 localStorage 상태에 원자적으로 저장. 실패하면 직전 도메인으로 되돌리고 미저장 후보를 내보낼 수 있다.
3. Google 연결 시 GET으로 revision 및 지원 기능을 확인한다. 오래된 자료·기준 없는 다른 자료는 업로드를 중단한다.
4. POST 전에 requestId, expectedRevision, 전체 후보를 독립 저장소에 남긴다. 응답이 유실되면 같은 후보와 requestId로 재시도한다.
5. GAS LockService 안에서 requestId 재사용과 revision을 검사한다. `_RentalSyncRecovery`에 이전 원문·해시·배치·청크 순서/전체 수를 저장하고 재조회한다.
6. Script Properties에 이전/새 해시와 복구 배치를 기록한 쓰기 journal을 남긴다. JSON을 35,000자 청크로 저장하고 잔여 행을 비운 뒤 다시 읽어 원문과 revision을 확인한다.
7. 원문이 journal의 이전 값도 새 값도 아니면 정상 JSON처럼 파싱되더라도 읽기·쓰기를 차단한다. 검증된 DB 저장 후 journal을 제거한다.
8. DB 결과와 Docs 결과를 별도로 반환한다. Calendar는 사용자 실행 시 저장된 DB만 사용한다. GAS는 JSON 문자열로 전송하여 중첩 null을 보존한다.

도메인의 알 수 없는 미래 필드를 older client가 지우지 않도록 보존했다. 초안·내보내기 시각·로컬 동기화 메타데이터는 도메인과 구분한다. 관리비 금액을 음수/소수/오류 문자열에서 임의의 0으로 바꾸던 처리도 차단했다. 금액의 쉼표 문자열은 보존하며 공통 계산 엔진에서 올바르게 읽는다. 기존 정상화 규칙 전체를 제거한 것은 아니다.

## 격리 검사

동일·다른 임차인에 대한 PC/모바일 두 클라이언트 충돌, 저장 직전 revision 변경, 동일 requestId 반복, 응답 유실 후 재실행, 오래된 탭, 오프라인 재연결, 복원 후 서버 불일치, 초안 기준 변경, 늦은 다운로드·응답 역전을 실제 클라이언트 경로로 검사한다.

서버에서는 복구 기록/재조회/해시 오류, 중간·마지막 청크, 잔여 행 삭제 실패, 손상된 JSON과 파싱 가능한 혼합 JSON, 복구 청크 누락/순서/원문 변경, 잠금 경합, 권한·quota 오류를 주입한다. 일부 실패는 활성 시트를 이전 상태로 유지하고, 부분 쓰기는 정상 결과를 반환하지 않고 검증된 이전 복구 원문을 남기며 차단한다. Sheets의 일반 트랜잭션이나 자동 완전 복구를 주장하지 않는다.

null·빈 문자열·0·과거 변경 이력·미래 루트 확장·보관/고아 고지서·금액 문자열·원 단위 배분·VAT 모드·납기·월말·날짜 검사 및 도메인 왕복을 검사한다. 부분입금 원장이나 새 계산 정책은 도입하지 않았다.

## Docs / Calendar

Docs의 BEGIN/END 밖 본문을 유지하고, 표시 누락·중복·훼손 시 중단한다. 같은 문서 ID를 사용한다. DB 성공/Docs 실패는 독립적이며 재생성은 DB 원문과 revision을 바꾸지 않는다. 생성 결과에 DB revision을 포함한다.

Calendar ID는 독립 Calendar에 고정한다. 개인/원본 Calendar fallback 및 자동 신규 Calendar 생성은 없다. 기존 매핑은 유지하고 새 tenant marker로 ID 조회 실패·매핑 손실·삭제 이벤트를 처리한다. marker가 없는 과거 일정은 같은 제목과 생성 설명이 정확히 일치할 때만 재사용한다. 불명확한 과거 일정이나 중복은 중단하며 자동 삭제하지 않는다. Google의 실제 권한/한도와 모든 Calendar 장애를 재현했다고 주장하지 않는다.

## 검증된 복구 절차

1. 다른 기기의 저장과 자동 동기화를 멈추고 활성 시트 원문, 복구 시트 및 Script Properties를 비공개로 보관한다. 현재 편집 후보와 초안도 JSON으로 내보낸다.
2. 상태 센터의 **최근 서버 복구점 점검**은 `inspectRecovery`로 전체 청크·배치·해시·도메인을 읽어 확인한다. 활성 데이터가 손상돼도 복구 점검이 가능하며 이 동작은 시트·문서를 쓰지 않는다.
3. 최신 복구 배치의 1~N 원문을 순서대로 이어 붙인다. 저장된 SHA-256 revision과 완전히 같고 JSON/도메인 검증이 통과하는지 별도 사본에서 확인한다. 누락/혼합/해시 불일치는 복원하지 않는다.
4. 실제 운영 복원은 별도 사용자 승인 대상이다. 승인 전에는 검증 원문과 복원 예상 변경을 제시한다. 새 시트에 검증 원문을 준비하거나 기존 활성 청크를 신중히 교체하고, 기록된 이전 해시와 정확히 일치할 때만 journal의 before 경로로 정상 읽기를 확인한다.
5. 모든 도메인을 재조회해 대조하고 새 기준 revision을 불러온다. DB 복구 확인 후 Docs와 Calendar를 각각 재실행한다. 복구 원문/기존 event ID를 삭제하지 않는다.

journal을 임의로 지우거나 빈 자료를 저장하여 오류를 없애지 않는다. 마지막 확인된 복구점은 마지막 성공 저장 이후의 기기 미반영 수정을 포함하지 않을 수 있다.

## 기준 실패 분류

기준 커밋에서 단위 85건 및 독립성 브라우저 7건 통과, 상속된 전체 브라우저 실패 7건을 재현했다. 수정 버튼 선택자·카카오 문구·승강기 net/gross 기대값·수동 배분 합계·과거 PWA 캐시 기대값은 낡은 기대값/시나리오였다. 충돌 POST와 작은 월 이동 터치 영역은 안전성/UX 결함이었다. 새 UI의 기하 구조는 사용자 요구에 따라 바뀌었으므로 기존과 픽셀 동일성 대신 새 경계와 기능 왕복을 검사하며 전후 캡처를 남긴다. 검사를 삭제하여 통과시킨 것이 아니다.

## 실 운영 자료와 미검증 범위

이 버전의 테스트는 익명 fixture, 임시 프로필, 모의 API와 Node VM 실패 주입으로 실행했다. 실제 시트에 테스트 저장, Calendar 테스트 일정 생성, Docs 갱신, GAS 운영 배포 교체, 원본 push는 하지 않았다.

종료 시 원본 시트 활성 원문을 초기 복제 기준과 대조하고, 원본 GAS 소스·배포 및 문서 수정일을 조회한다. 복제본의 현재 4명·11개월 도메인은 원본과 일치했으며 현재 데이터에 구/신 validator를 적용한 결과 차이가 없었다. 모든 Drive 파일의 전체 revision 이력, Calendar의 모든 업무 외 이벤트, 실제 Google 장애/동시 쓰기와 2.0 운영 저장은 미검증이다. 최종 판정은 RELEASE_CANDIDATE_V2.md에 기록한다.

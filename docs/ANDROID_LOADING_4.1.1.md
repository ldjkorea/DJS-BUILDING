# Android 4.1.1 연결·로딩 개선

NEW RENT STORE의 네이티브 앱에서 서버 확인 중에도 보관 자료를 조회하고, 반복 조회에 따른 대기를 줄인다. 원본 RENT STORE·2025 RENT STORE, 웹 2.3.0 UI, 임대 데이터 구조와 거래 규칙은 유지한다.

## 확인한 지연과 변경

- 운영 Android API의 메타데이터 GET 3회는 2,898~3,315ms, 토큰 없는 read POST 3회는 2,728~4,986ms였다. Windows에서 HTTP 리다이렉트와 응답 본문을 포함해 측정했다. 인증된 임대 자료 조회와 실제 휴대폰의 소요 시간은 측정하지 않았으므로 이 수치를 전체 조회 시간으로 해석하지 않는다.
- 홈은 암호화된 보관 자료를 먼저 표시한다. 서버 확인 중에도 홈·세입자·고지서·설정 메뉴, 검색과 읽기 전용 상세 조회를 허용한다. 입금·지출·계약·정산 등의 변경은 확인 완료 전까지 차단한다.
- `connected()`가 렌더링 중 반복해서 암호화된 전체 세션을 읽던 동작을 연결 여부의 메모리 상태로 바꿨다. 토큰 자체는 계속 기존 암호화 세션에 보관한다.
- 같은 프로세스에서 서버 확인을 마친 자료만 최대 30초 재사용한다. 기기 토큰의 해시, 조회 월, 한국 날짜, 전체 스냅샷 해시가 모두 맞아야 한다. 단순히 디스크에 남아 있는 자료는 저장 권한을 주지 않는다. 저장 결과 미확인, 저장 시작, 연결 해제, 오류, 날짜 변경, 프로세스 종료 시 재사용하지 않는다.
- 같은 기기·월의 진행 중인 조회는 한 요청을 공유한다. 수동 새로고침은 재사용 기한 안에서도 서버를 확인한다. 조회 응답 JSON은 각 호출자에게 별도 객체로 전달한다.
- `read`에 `knownRevision`·`knownToday`를 보낼 수 있다. 서버는 기존 기기 인증과 잠금을 수행하고 실제 시트를 읽어 검증한 뒤, 정확히 같은 revision과 날짜일 때만 `unchanged:true`를 반환한다. 클라이언트는 protocol·revision·월·날짜가 모두 맞는 응답에만 기존 자료를 사용한다. 원본 시트 대신 오래된 서버 캐시를 읽는 방식은 사용하지 않는다.
- 새 앱의 저장 요청은 `includeSnapshot:true`를 보낸다. 기존 조건부 저장·복구·저장 후 검증·문서 상태 응답에 `latest`를 함께 넣어, 정상적인 저장 후 네트워크 호출을 2회에서 1회로 줄인다. 구형 서버는 기존 방식으로 후속 조회한다. 구형 앱에는 기존 응답을 유지한다.
- 저장 성공과 후속 조회 실패를 구분한다. 조회가 실패해도 저장 성공 응답을 바꾸지 않고, 앱은 결과 확인이 필요하다고 표시하며 `pending`을 유지한다. 저장 요청은 자동 재전송하지 않는다.
- 계약·정산 등 작업 화면에는 진행 상태를 표시하고, 연결 중에도 뒤로 이동할 수 있게 했다. 입력 초안의 기존 암호화 보관 방식은 유지한다.
- 일반 조회는 리다이렉트 전체에 45초의 시간 예산을 적용하고 연결·읽기 시간 제한을 줄였다. 저장과 APK 다운로드의 기존 시간 제한·재전송 금지는 유지한다.

## 검증 범위

- Node 자동 검사 225개 통과. 조건부 조회의 실제 저장소 검증·권한 해제·날짜/revision 변경, 묶음 저장 응답·문서 오류 독립성·후속 조회 실패·구형 APK 호환을 포함한다.
- Android 빌드·단위 검사·release lint 통과. lint 0 errors / 기존 6 warnings.
- 전용 API 35 에뮬레이터에서 최신 자료 재사용의 만료·계정/월/날짜/스냅샷 변경·pending, 수동 새로고침, 중복 요청, 저장 시작 후 늦은 조회 무효화, 잘못된 서버 응답, 암호화 파일 보존, 느린 연결 중 메뉴/상세 조회와 저장 차단을 검증한다.
- 시험 APK의 버전·이름은 실제 파일에서 읽어 검증한다. 시험 파일은 androidTest에만 들어가며 운영 APK에 포함하지 않는다.
- 운영 임대 자료를 변경하는 테스트는 하지 않는다. 에뮬레이터의 자료는 합성 예시다. 실제 휴대폰·프린터, 인증된 임대 조회의 전후 시간은 별도 확인이 필요하다.

전체 속도가 몇 배 개선됐다고 단정하지 않는다. 검증한 개선은 불필요한 요청 제거, 조회 중 UI 사용, 엄격한 자료 재사용과 저장 결과 구분이다. 첫 Google 연결, 새 프로세스의 첫 서버 조회, 시트/문서/Calendar 작업에는 서버 실행 시간이 남는다.

Google도 서비스 호출 최소화와 일괄 작업을 성능 개선의 우선 원칙으로 안내한다: [Apps Script Best Practices](https://developers.google.com/apps-script/guides/support/best-practices).
